Поток данных и интеграция с базой данных в OpenBioMaps
******************************************************

На этой странице описано, как OpenBioMaps связывает конфигурацию проекта,
объекты базы данных PostgreSQL, метаданные, процессы загрузки, правила
доступа, запросы и внешние клиенты.

Она предназначена для разработчиков, администраторов серверов и опытных
администраторов проектов, которым необходимо понимать техническую реализацию
пользовательского процесса управления данными. Общее введение в сбор данных
и управление ими см. в следующих разделах:

* :doc:`Начало работы <getting_started>`;
* :doc:`Сбор данных <data_collection>`;
* :doc:`Управление данными <data_management>`; и
* :doc:`Доступ к данным <data_access>`.

Описанные здесь детали реализации могут различаться в зависимости от версии
OpenBioMaps и конфигурации проекта. Перед непосредственным изменением
объектов базы данных изучите текущие метаданные проекта, триггеры,
представления, правила доступа и исходный код приложения. Тестируйте
структурные изменения в отдельном проекте и создавайте подходящую резервную
копию перед их применением к рабочим данным.


Технический обзор
=================

Типичный поток данных OpenBioMaps включает следующие технические этапы:

#. Администратор проекта определяет таблицы, столбцы и связи PostgreSQL, а
   также метаданные OpenBioMaps.
#. Формы загрузки предоставляют выбранные столбцы веб-клиентам, средствам
   загрузки файлов, API или мобильным клиентам.
#. Клиент отправляет записи и, если применимо, вложения и метаданные
   загрузки.
#. OpenBioMaps проверяет и преобразует отправленные значения в соответствии
   с определением формы.
#. Приложение вставляет принятые значения в целевую таблицу и регистрирует
   сведения о загрузке.
#. Триггеры базы данных или фоновые задания могут поддерживать историю,
   правила доступа, таксономические данные, производные значения и другие
   структуры, относящиеся к конкретному проекту.
#. Шаблоны запросов объединяют таблицы проекта с фрагментами контроля доступа
   и модулей.
#. Полученные данные можно отображать через веб-приложение или получать с
   помощью экспорта, API, клиентов SQL и других интеграций.
#. Резервные копии, архивы и политика проекта определяют, как сохраняются
   данные и связанная с ними конфигурация.

Не каждый проект использует все эти этапы. Например, небольшой проект может
использовать одну таблицу наблюдений и одну веб-форму, тогда как проект
мониторинга может использовать отдельные таблицы для мест, событий,
наблюдений, таксонов, вложений и результатов проверки.


Серверная часть PostgreSQL
==========================

OpenBioMaps хранит данные проекта в PostgreSQL и обычно использует PostGIS
для пространственных данных. База данных содержит как обычные объекты
PostgreSQL, так и метаданные OpenBioMaps, описывающие, как приложение должно
использовать эти объекты.

Само по себе существование таблицы или столбца PostgreSQL не делает этот
объект доступным в OpenBioMaps. Соответствующие метаданные также должны
идентифицировать объект и описывать его роль в проекте.


Таблицы базы данных и метаданные
--------------------------------

Таблицы, созданные через интерфейс администрирования проекта, создаются в
PostgreSQL и регистрируются в метаданных OpenBioMaps. После этого
зарегистрированные таблицы можно использовать в формах загрузки, шаблонах
запросов, модулях, административных инструментах и других компонентах
приложения.

Таблица или представление, созданные с помощью клиента SQL, автоматически не
регистрируются. Их необходимо добавить в соответствующие метаданные
OpenBioMaps, прежде чем приложение сможет безопасно и согласованно их
использовать.

Для поддерживаемых операций с таблицами следует предпочитать интерфейс
администрирования, поскольку он может обновлять как объект PostgreSQL, так и
связанные с ним метаданные. Непосредственные изменения SQL могут привести к
тому, что метаданные, формы, запросы, триггеры или модули будут ссылаться на
объект, который больше не существует.

Описания таблиц
---------------

Зарегистрированная таблица может иметь понятное человеку описание. Описания
таблиц и столбцов являются частью метаданных проекта и должны объяснять
смысл, происхождение, единицы измерения, ожидаемые значения и предполагаемое
использование данных.

Настоятельно рекомендуется добавлять описания, даже если технически они не
являются обязательными. Структуру базы данных, которую можно понять только
по её идентификаторам SQL, сложно сопровождать, передавать и повторно
использовать.

Рекомендации по метаданным и происхождению данных см. в разделах
:doc:`Управление данными <data_management>` и
:doc:`Политика управления данными <data_policy>`.


Столбцы базы данных
-------------------

Таблица проекта состоит из обычных столбцов данных и, при необходимости,
системных столбцов OpenBioMaps. PostgreSQL определяет физический тип данных,
ограничения и способ хранения каждого столбца. Метаданные OpenBioMaps
определяют, как приложение интерпретирует и использует столбец.


Системные столбцы
.................

Таблицы, созданные OpenBioMaps, обычно содержат столбцы с префиксом
``obm_``. В зависимости от версии OpenBioMaps и конфигурации проекта к ним
могут относиться поля:

``obm_id``
   Внутренний идентификатор записи.

``obm_geometry``
   Пространственная геометрия, связанная с записью.

``obm_uploading_id``
   Ссылка на загрузку, в рамках которой была создана запись.

``obm_validation``
   Информация, связанная с проверкой.

``obm_comments``
   Комментарии или аннотации, связанные с записью.

``obm_modifier_id``
   Информация, идентифицирующая пользователя или процесс, изменивший запись.

``obm_files_id``
   Ссылка или ссылки, связанные с загруженными вложениями.

Базовое определение таблицы может выглядеть следующим образом:

.. code-block:: sql

   CREATE TABLE public.test_table (
       obm_id integer
           DEFAULT nextval(
               'public.test_table_obm_id_seq'::regclass
           )
           NOT NULL,
       obm_geometry public.geometry,
       obm_uploading_id integer,
       obm_validation numeric,
       obm_comments text[],
       obm_modifier_id integer,
       obm_files_id character varying(32),
       CONSTRAINT enforce_dims_obm_geometry
           CHECK (public.st_ndims(obm_geometry) = 2),
       CONSTRAINT enforce_srid_obm_geometry
           CHECK (public.st_srid(obm_geometry) = 4326)
   );

Этот пример приведён исключительно для иллюстрации и не должен
рассматриваться как авторитетная схема для каждой установки. Типы столбцов,
ограничения, обработка вложений, определения последовательностей и настройки
системы пространственных координат могут различаться между версиями и
проектами.

Не удаляйте и не переименовывайте столбец ``obm_`` только потому, что он
кажется неиспользуемым. От него могут зависеть обработка загрузок, триггеры,
модули, правила доступа, история, запросы или внешние клиенты.

Типы PostgreSQL и типы OpenBioMaps
..................................

Тип данных PostgreSQL описывает способ хранения значения и операции базы
данных, которые можно выполнять над ним. К примерам относятся ``text``,
``integer``, ``date``, ``timestamp``, массивы и типы геометрии PostGIS.

Тип столбца или семантическая роль OpenBioMaps описывает, как приложение
использует столбец. Например, столбец может представлять:

* общее значение данных;
* научное название;
* альтернативное название таксона;
* дату наблюдения;
* количество особей;
* геометрию;
* координату;
* ссылку на источник; или
* вложение.

Компоненты приложения, такие как формы загрузки и интерфейсы запросов, могут
выбирать только зарегистрированные столбцы, доступные через метаданные
OpenBioMaps.

Тип PostgreSQL и семантическая роль OpenBioMaps должны быть совместимы.
Назначение семантической роли не преобразует физический тип данных и не
проверяет автоматически существующие значения.

Идентификаторы и видимые названия столбцов
..........................................

В идентификаторах PostgreSQL следует использовать строчные буквы, цифры и
символы подчёркивания. Избегайте пробелов, букв с диакритическими знаками,
идентификаторов в кавычках и других специальных символов. Метаданные
OpenBioMaps могут связывать со столбцом отдельное видимое название, поэтому
безопасный для базы данных идентификатор необязательно отображать
пользователям напрямую.

Например, столбец базы данных может называться ``observation_date``, а его
видимое название может отображаться как ``Observation date`` или его
перевод.

Видимое название, начинающееся с префикса ``str_``, можно использовать как
ключ перевода там, где поддерживается относящаяся к проекту локализация.
Клиентское приложение отображает перевод, доступный для текущего языка, а
при отсутствии перевода применяется настроенное резервное поведение.

Изменение только видимого названия не переименовывает столбец PostgreSQL.
Переименование столбца PostgreSQL может нарушить работу форм, запросов,
триггеров, представлений, модулей, экспортов и внешних клиентов.

Дополнительную информацию о локальных переводах см. в разделе
:ref:`Локальные переводы <localisation>`.

Порядок столбцов
................

PostgreSQL сохраняет физический порядок столбцов в определениях таблиц, но не
предоставляет простой поддерживаемой операции для изменения порядка
существующих столбцов. Метаданные OpenBioMaps и формы загрузки могут
определять порядок представления независимо от физического порядка в базе
данных.

Порядок на уровне проекта можно использовать по умолчанию в представлениях
данных и формах. Отдельная форма загрузки может переопределить этот порядок
для собственного процесса. Если порядок на уровне приложения не определён,
интерфейс может использовать порядок базы данных или метаданных.

Не создавайте рабочую таблицу повторно только для изменения видимого порядка
её столбцов, если для этого нет подтверждённого технического требования.
Повторное создание таблицы может повлиять на:

* последовательности и значения по умолчанию;
* первичные и внешние ключи;
* индексы и ограничения;
* владельцев и привилегии;
* триггеры и правила;
* комментарии и метаданные;
* представления и материализованные представления;
* таблицы правил доступа;
* формы загрузки и шаблоны запросов; и
* внешние приложения.

По возможности используйте настройки порядка представления OpenBioMaps.

Ввод данных
===========

Данные проекта могут поступать в PostgreSQL через процессы загрузки
OpenBioMaps или посредством непосредственных операций с базой данных. Эти
способы не являются эквивалентными.


Процессы загрузки OpenBioMaps
-----------------------------

Формы загрузки определяют целевую таблицу, доступные столбцы, обязательные
поля, элементы ввода, значения по умолчанию, правила проверки,
поддерживаемые клиенты и настройки доступа.

В зависимости от конфигурации форма может использоваться:

* веб-интерфейсом ввода данных;
* процессом загрузки файлов;
* API OpenBioMaps;
* мобильным приложением; или
* другим совместимым клиентом.

Типичный ввод данных с помощью формы включает следующие этапы:

#. Клиент получает или отображает определение формы.
#. Участник вводит или загружает значения.
#. Приложение проверяет структуру и значения отправленных данных.
#. Там, где это поддерживается, отображаются предупреждения или
   некритические ошибки проверки.
#. Принятые значения записываются в целевую таблицу.
#. Регистрируются метаданные загрузки.
#. Если применимо, сохраняются вложения и их связи.
#. Триггеры базы данных выполняют настроенные последующие операции.

Подробную информацию о настройке форм см. в разделе
:doc:`Управление формами загрузки <upload_forms>`.


События загрузки и происхождение данных
---------------------------------------

Когда данные отправляются через процесс загрузки OpenBioMaps, приложение
регистрирует сведения о загрузке в таблице ``system.uploadings``. Записи,
добавленные в управляемую таблицу данных, могут ссылаться на эту загрузку
через ``obm_uploading_id``.

Метаданные загрузки можно использовать для связи записей с такими
сведениями, как:

* участник или владелец;
* целевая таблица;
* форма, использованная для загрузки;
* время отправки;
* назначения групп доступа;
* исходный файл или процесс ввода данных; и
* состояние обработки или завершения.

Точные сохраняемые поля и их смысл зависят от версии. Непосредственная
вставка SQL не создаёт автоматически эквивалентное событие загрузки, если
вызывающая сторона явно не реализует необходимый процесс.

Проверка и преобразование
-------------------------

Проверка может выполняться на нескольких уровнях:

* элементы управления формы на стороне клиента;
* серверная обработка загрузки;
* типы и ограничения PostgreSQL;
* триггеры базы данных;
* фоновые задания; и
* последующая проверка куратором.

Проверка на стороне клиента повышает удобство использования, но не должна
рассматриваться как граница безопасности. Значения, полученные через API,
загрузку файлов или непосредственные подключения к базе данных, требуют
соответствующей проверки на стороне сервера.

Преобразования могут нормализовать значения, создавать геометрию, разрешать
таксономические названия, назначать значения по умолчанию или вычислять
другие поля. Если преобразование изменяет научный смысл отправленных данных,
проект должен сохранять исходное значение или достаточные сведения о
происхождении, позволяющие восстановить изменение.

Информацию о фоновой обработке см. в разделе
:doc:`Фоновые задания <jobs>`.


Непосредственный ввод SQL
-------------------------

Авторизованные пользователи базы данных могут вставлять или импортировать
записи с помощью клиентов PostgreSQL и таких инструментов, как ``COPY``.
Это может быть полезно для контролируемого массового переноса или
административного исправления данных.

Например, PostgreSQL поддерживает импорт данных с помощью ``COPY FROM``.
См. `документацию PostgreSQL по COPY
<https://www.postgresql.org/docs/current/sql-copy.html>`_.

Непосредственные операции SQL могут обходить поведение уровня приложения,
включая:

* проверку формы загрузки;
* автоматическое создание метаданных загрузки;
* обработку вложений;
* назначения правил доступа;
* сведения об истории или аудите;
* относящиеся к проекту преобразования;
* уведомления; и
* обработку ошибок на уровне приложения.

Триггеры базы данных всё равно выполняются, если они не отключены, однако их
поведение может зависеть от значений, обычно передаваемых приложением.
Поэтому запись, вставленная без ``obm_uploading_id`` или другого ожидаемого
поля, может получить неполные метаданные или правила доступа.

При непосредственном импорте данных рекомендуется создать пустую загрузку,
затем назначить идентификатор загрузки (``obm_uploading_id``) импортированным
данным и указать в метаданных загрузки непосредственный метод и источник
загрузки.

Перед непосредственным импортом:

#. изучите целевую таблицу, ограничения, триггеры и правила;
#. определите, требуется ли соответствующая запись загрузки;
#. явно проверьте и преобразуйте исходные данные;
#. при необходимости используйте транзакцию;
#. протестируйте импорт в нерабочем проекте;
#. проверьте доступ на уровне строк и столбцов после вставки;
#. проверьте процессы истории, вложений и таксономии; и
#. зарегистрируйте источник и преобразование импортированных данных.

Не отключайте триггеры только для того, чтобы импорт завершился успешно, не
поняв предварительно их назначение. Триггеры контроля доступа, истории или
целостности могут иметь критическое значение для безопасности.

Триггеры, правила и производная обработка
=========================================

Проекты OpenBioMaps могут использовать триггеры и правила PostgreSQL для
поддержки относящегося к проекту поведения при вставке, обновлении или
удалении записей.

К задокументированным процессам триггеров относятся:

* поддержка списка таксонов;
* история записей;
* правила построчного доступа; и
* относящиеся к проекту проверки или производные значения.

Триггер работает внутри транзакции базы данных и может отклонить или изменить
операцию. Фоновое задание обычно выполняется отдельно и лучше подходит для
длительной, плановой, повторяемой после ошибки или ресурсоёмкой обработки.

Это различие имеет важное значение:

``Constraint``
   Обеспечивает соблюдение инварианта базы данных и отклоняет значения,
   которые ему не соответствуют.

``Trigger``
   Выполняется автоматически как часть изменения базы данных.

``Rule``
   Переписывает или перенаправляет выбранные операции PostgreSQL, включая
   операции над настроенными представлениями.

``Background job``
   Выполняется отдельно по расписанию или после запуска вручную.

``Application validation``
   Проверяет или преобразует значения в процессе OpenBioMaps на уровне
   приложения.

Одно и то же требование не следует реализовывать несогласованно на нескольких
уровнях. Если необходимо использовать несколько уровней, их обязанности и
поведение при ошибках должны быть задокументированы.

Информацию об администрировании триггеров см. в разделе
:ref:`Функции <trigger-functions>`.

Интеграция правил доступа
=========================

Доступ к данным проекта может контролироваться посредством настроек проекта
по умолчанию, правил на уровне строк, ограничений на уровне столбцов,
членства в группах и административных ролей.

Процесс построчного доступа обычно связывает:

* ``obm_id`` записи;
* соответствующий ``row_id`` в таблице правил проекта;
* название целевой таблицы;
* назначения на чтение и запись;
* значение конфиденциальности; и
* метаданные загрузки или владельца.

Триггер правил доступа может определять назначения на основе формы загрузки
и связанной записи в ``system.uploadings``. Записи, созданные непосредственно
с помощью SQL, необязательно содержат метаданные, необходимые для такого
определения.

Шаблон запроса также должен содержать соответствующие фрагменты контроля
доступа. Корректные правила в базе данных не защищают данные, если запрос
приложения или внешнее подключение обходит их.

Вывод данных
============

OpenBioMaps может предоставлять данные проекта через веб-интерфейс, карты,
API, экспорты, сохранённые результаты и внешние клиенты базы данных. Каждый
способ необходимо оценивать отдельно с точки зрения контроля доступа,
метаданных, названий полей и формата вывода.


Веб-запросы и карты
-------------------

Веб-приложение использует настроенные шаблоны запросов SQL для формирования
текстовых и пространственных результатов запросов. Шаблоны могут содержать
местозаполнители для:

* выбранных полей;
* пространственной фильтрации;
* дополнительных фильтров модулей;
* таксономических соединений;
* метаданных загрузки;
* соединений правил доступа; и
* других фрагментов SQL, относящихся к проекту.

Слои MapServer могут использовать динамически создаваемые запросы для
отображения тех же данных проекта на карте. Запрос PostgreSQL, mapfile
MapServer, слой веб-карты и конфигурация запросов OpenBioMaps должны
оставаться согласованными.

Неправильно настроенный запрос может пропустить записи, продублировать
строки, раскрыть ограниченные поля или обойти ожидаемое соединение с
правилами доступа. Каждую конфигурацию запроса следует тестировать от имени:

* неаутентифицированного посетителя;
* обычного аутентифицированного пользователя;
* участника каждой соответствующей группы;
* владельца записи или участника, предоставившего данные; и
* администратора.

Подробную информацию см. в разделах
:ref:`Настройки запросов SQL <sql-query-settings>` и
:ref:`Настройки карты <map-settings>`.


Экспорт
-------

Результаты запросов или полные таблицы можно экспортировать в поддерживаемых
форматах. Небольшие экспорты могут создаваться во время интерактивного
запроса, а более крупные — передаваться фоновому заданию.

В процессе экспорта следует сохранять или включать:

* выбранные записи и поля;
* применённые фильтры;
* время запроса или экспорта;
* метаданные проекта и набора данных;
* сведения о лицензии и атрибуции;
* применимые сведения о системе пространственных координат;
* происхождение данных; и
* любые условия конфиденциальности или повторного использования, которые
  должны понимать получатели.

Созданные файлы могут оставаться доступными после завершения исходного сеанса
пользователя. Поэтому место их хранения, разрешения на скачивание, срок
действия и очистка являются частью модели безопасности.

Доступ через API
----------------

API OpenBioMaps предоставляет программный доступ к поддерживаемым операциям
проекта. Клиенты API могут получать определения форм, отправлять данные,
выполнять запросы к записям или другие авторизованные операции в зависимости
от версии API и предоставленной области доступа.

Отправка данных через API с использованием опубликованной формы загрузки
должна следовать серверному процессу формы. Непосредственная интеграция с
базой данных не эквивалентна отправке через API и может приводить к созданию
других метаданных и иному поведению триггеров.

Подробную информацию см. в разделе
:doc:`Документация API <api>`.


Клиенты SQL и внешние приложения
--------------------------------

PostgreSQL, если оператор сервера и проекта явно предоставляет учётные
данные и сетевой доступ.

безопасность не воспроизводят модель доступа приложения. Не следует считать,

применяются к произвольным подключениям SQL.

предпочтительно использовать отдельные роли базы данных только для чтения,

Пользователи, роли и идентификаторы базы данных
===============================================

Пользователи приложения OpenBioMaps, роли проекта, группы, клиенты OAuth и
роли PostgreSQL являются связанными, но не взаимозаменяемыми понятиями.

``Application user``
   Человек или сервис, представленный учётной записью OpenBioMaps.

``Project membership``
   Связывает пользователя приложения с определённым проектом и статусом.

``Project group``
   Объединяет пользователей приложения для предоставления доступа к формам,
   данным, модулям или административным функциям.

``Administrative role``
   Предоставляет доступ к выбранным функциям администрирования проекта.

``OAuth client or token``
   Авторизует клиентское приложение действовать в пределах предоставленных
   областей доступа.

``PostgreSQL role``
   Контролирует непосредственную аутентификацию в базе данных и привилегии
   SQL.

Пользователь, который может запрашивать запись через веб-приложение, не
получает автоматически непосредственный доступ к PostgreSQL. И наоборот,
роль PostgreSQL с широкими привилегиями на таблицы может обходить
ограничения, реализованные только в приложении.

Для служебных учётных записей и автоматизированных интеграций следует
использовать отдельные учётные данные только с теми привилегиями, которые
необходимы для их функций. Токены и пароли базы данных не следует встраивать
в исходный код или использовать совместно в несвязанных приложениях.

Безопасные изменения схемы
==========================

Изменения управляемой таблицы могут влиять как на PostgreSQL, так и на
конфигурацию OpenBioMaps. Перед переименованием, заменой или удалением
таблицы или столбца:

#. определите использующие объект формы загрузки;
#. выполните поиск в шаблонах запросов и mapfile MapServer;
#. изучите триггеры, правила, представления, индексы, ограничения и внешние
   ключи;
#. изучите семантические роли столбцов и метаданные проекта;
#. изучите конфигурацию правил доступа и истории;
#. определите модули и фоновые задания, ссылающиеся на объект;
#. определите клиентов API, мобильных приложений, QGIS, R и
   непосредственного SQL;
#. создайте и проверьте подходящую резервную копию;
#. протестируйте миграцию в отдельном проекте;
#. определите процедуру отката; и
#. проверьте все поддерживаемые интерфейсы после миграции.

Для поддерживаемых операций используйте интерфейс администрирования. Если
необходим непосредственный SQL, обновите соответствующие метаданные
OpenBioMaps и зависимую конфигурацию в рамках той же контролируемой миграции.

Переименование объекта необязательно безопаснее его удаления и повторного
создания: обе операции могут нарушить зависимости, в которых исходный
идентификатор хранится в виде текста.

Контрольный список технической проверки
=======================================

После создания или изменения процесса работы с данными проекта убедитесь,
что:

* каждый управляемый объект PostgreSQL имеет необходимые метаданные
  OpenBioMaps;
* системные столбцы имеют ожидаемые типы, ограничения и значения по
  умолчанию;
* последовательности, ключи, индексы, триггеры и правила действительны;
* определения форм ссылаются на существующие целевые столбцы;
* проверка формы также соответствующим образом выполняется на сервере;
* метаданные загрузки создаются и связываются со вставленными записями;
* вложения связываются с предполагаемыми записями;
* непосредственные импорты получают соответствующие сведения о
  происхождении и правила доступа;
* триггеры истории и таксономии создают ожидаемые результаты;
* общедоступные и относящиеся к группам запросы обеспечивают соблюдение
  ограничений строк;
* ограниченные столбцы отсутствуют во всех неавторизованных результатах;
* слои карты и текстовые запросы возвращают согласованные записи;
* отправка через API и мобильные приложения использует предполагаемую
  опубликованную версию формы;
* роли SQL не могут читать или изменять больше данных, чем предусмотрено;
* созданные экспорты защищены и удаляются в соответствии с политикой;
* фоновые задания выполняются с необходимыми зависимостями и минимальными
  привилегиями;
